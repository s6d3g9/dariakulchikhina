# ADR-0011: Vue/Nuxt renderer для apps/shell-web (форк v6-shell)

- **Статус**: Accepted
- **Дата**: 2026-07-02
- **Решение**: форк v6-shell реализует первый experience-слой (apps/shell-web) на Vue 3 / Nuxt 4 SPA; framework-нейтральные контракты остаются в packages/*
- **Ответственный**: solo-разработка (owner) + Claude-сессии
- **Связано**: ADR-0007 (Expo vs native), docs/architecture-v6/01-stack.md, 05-shell-entity-model.md, 09-invariants.md, 17-fractal-ux.md

## Контекст

v6 (docs/architecture-v6/) предписывает для experience-слоя React/Next.js + Expo + Tauri, но сам зафиксирован как **DRAFT** («не руководство к действию, а основа для обсуждения»). Реальные активы на момент старта форка:

- messenger-refactor web — живой прод на **Vue 3 / Nuxt 4** (SPA, ssr:false), с отработанными паттернами (runtime-инъекция API base, плита 64px, рейлы, реестры);
- Mac-версия — Electron, производная от web-бандла (наследуется автоматически);
- Android — нативный Kotlin (androidlouncher), свой релиз-цикл;
- команда — один человек; React/Expo/Tauri-компетенций и команды под них нет.

Цель форка — альтернативная самоподобная версия системы (shell + card-types) поверх живых данных messenger-refactor, без слома прод-мессенджера. Смена рендерера на React обнулила бы переиспользование единственного живого фронтового актива и навсегда добавила бы третий стек к Vue+Kotlin.

## Альтернативы

### React/Next.js (канон 01-stack)

Плюсы: соответствие букве доков v6; RN Web adapter в перспективе (ADR-0007); hiring pool.
Минусы: ноль переиспользования кода/паттернов messenger-web; обрыв цепочки web→Electron; третий стек для solo-разработчика; медленнее до первого экрана.

### Vue 3 / Nuxt 4 (выбрано)

Плюсы: переиспользование живых паттернов и цепочки web→Mac; скорость до первого экрана; один фронтовый стек в хозяйстве.
Минусы: отступление от буквы 01-stack; будущий shell-mobile на Expo (ADR-0007) не разделит UI-код с shell-web.

## Решение

1. **Рендерер = деталь реализации experience-слоя.** Инварианты v6 (I1 вертикаль=card-types-пакет, I3 dual-view, I15 EntityProvider, I19 две ручки, I21 timeline, I23 contract+fractal тесты) — framework-нейтральны и проверяются тестами/контрактами, а не выбором фреймворка. Дух канона соблюдается harness'ом, буква (React) — осознанно нарушается.
2. **Граница стека**: `packages/*` — только чистый TypeScript, ноль импортов Vue/React (проверка: `grep -rn "from 'vue'" packages/` == 0). Всё Vue-специфичное — только внутри `apps/shell-web`.
3. **Workspace-изоляция**: корень репозитория НЕ переводится в pnpm-workspace (в корне нет pnpm-workspace.yaml, и её появление сменило бы семантику install/lockfile для v5.3-приложения). `apps/shell-web` — самодостаточный пакет со своим package.json и lockfile; контракты из `packages/*` подключаются относительными путями через tsconfig paths/vite alias. Пересмотр — отдельным ADR, если пакетов станет ≥3.
4. **Данные**: shell-web ↔ messenger-refactor core только по HTTP (/refactor/api); никаких импортов кода core и никакого прямого доступа к БД (в духе правила №2 v5.3 и I6 v6).
5. ADR-0007 (Expo для mobile) не пересматривается: он относится к Фазе 3 v6. Для форка Android-путь: WebView-вход → нативный Compose-рендерер JSON-контрактов card-types (наследует API и контракты, не UI-код).

## Критерии отката (любой → стоп и ревизия этого ADR)

1. Появилась команда/подрядчик под React/Expo/Tauri и решение о переходе на канон 01-stack.
2. Vue-специфика протекла в `packages/*` (grep-чек красный) и не убирается за одну сессию.
3. Кол-во UI-платформ, дублирующих логику руками, превысило 2 (web+android) — нужен общий слой, решаем заново.
