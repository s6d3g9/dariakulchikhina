# 05. Shell и модель сущностей

Ключевой принцип всего UX v6: **любая сущность — это универсальная карточка в persistent-shell, у которой есть два представления (instance и type), и переключение между ними перерисовывает все 4 панели shell'а**.

Это обобщение того, что изначально описывалось для «зайти в профиль человека → панели показывают его контент». На самом деле оно работает для **всего**: людей, компаний, автомобилей, квартир, питомцев, курсов, модулей кода, игр, брендов.

## 1. Persistent mobile shell

Мобильное приложение — это shell с 5 областями:

```
┌───────────────────────────────┐
│  ⬆ top-panel  (stories/feed)  │
├──┬─────────────────────────┬──┤
│◀ │                         │ ▶│
│  │      CENTER CARD        │  │
│le│   (Pattern-Card +       │ri│
│ft│    Timeline + Mode)     │gh│
│  │                         │  │
├──┴─────────────────────────┴──┤
│  ⬇ bottom-panel (twitter-lite)│
└───────────────────────────────┘
```

4 периферийные панели + центр. Центр — Pattern-Card текущего контекста. Периферия свайпается, сам shell не уходит.

**Дефолтный «свой» контекст (я, как пользователь):**

| Область | Содержимое |
|---|---|
| Top | Stories / галереи / игры — мои + от тех, на кого подписан |
| Left | Shop / wallet — мои покупки, подписки, активы |
| Center | Switcher модулей (messenger, travel, dating, …) + активная карточка |
| Right | Messenger — мои чаты |
| Bottom | Twitter-feed — мои посты и лента |

## 2. Правило контекстной инверсии

Центральная карточка — всегда «кто/что сейчас в фокусе». Когда фокус меняется (зашёл в профиль, открыл карточку машины, выбрал курс), **все 4 периферийные панели автоматически переключаются в контекст этой сущности**.

Это работает единообразно: не важно, человек это, компания, товар или модуль кода.

## 3. Два представления: Instance и Type

Каждая сущность имеет **два канонических вида**, переключаемых кнопкой инверсии ⇄ на центральной карточке:

| Вид | Суть | Пример (автомобиль) |
|---|---|---|
| **Instance** | Конкретный экземпляр / «моё» / «это» | Мой Toyota Camry, VIN …123 |
| **Type** | Класс / модель / продукт / бренд | Toyota Camry 2023 (модель вообще) |

Переключение не открывает новый экран — это **ре-рендер 4 панелей shell'а** с другой семантикой.

## 5. Режимы (modes) внутри instance и type

На каждой стороне инверсии может быть ещё **mode**-переключатель (уже описывался для travel: `creator` / `marketplace`):

- **Instance + consumer mode** — я как владелец/пользователь.
- **Instance + provider mode** — я сдаю свою машину в аренду, мой дом — в airbnb, мой питомец — на вязку. Те же панели, но с точки зрения провайдера: календарь, заявки, выручка.
- **Type + explore mode** — изучаю продукт.
- **Type + buy mode** — готов купить/подписаться.

Mode — вторичное измерение; основное — **инверсия instance ⇄ type**.

## 6. Почему это важно архитектурно

Это не UI-фича. Это **принцип моделирования данных** во всём v6:

1. Каждая сущность в системе имеет **две проекции** в каталоге сервисов: `instance_view` и `type_view`.
2. `ownership-registry` связывает `instance → type` (мой VIN 123 → модель Toyota Camry 2023).
3. `authorship-registry` — частный случай: `instance_of_digital_asset → template_type` (моя фотография → шаблон-паттерн, от которого она породилась).
4. Панели shell'а подписаны на **потоки, параметризованные по `(entity_id, view_mode)`**. Panel-provider плагины знают, как рендерить поток для `(car, instance)` vs `(car, type)`.
5. Один и тот же code-path обслуживает people, cars, real-estate, pets, courses — разница только в type-plugin для каталога карточек.

## 7. Следствия для сервисов

Инверсия требует, чтобы **для каждого card-type** были описаны оба view:

```
packages/card-types/car/
  instance.view.ts      # моя машина: maintenance, budget, trips
  type.view.ts          # модель: specs, community, shop
  panels/
    top.instance.ts     # галерея моей машины
    top.type.ts         # галерея модели
    left.instance.ts    # бюджет + сервисы моего конкретного экземпляра
    left.type.ts        # shop для модели
    right.instance.ts   # чаты про мою машину
    right.type.ts       # сообщества модели
    bottom.instance.ts  # мой журнал
    bottom.type.ts      # feed модели
```

Это шаблон `packages/card-types/*`: каждый плагин обязан реализовать `instance.view` и `type.view` + 8 panel-providers (4 панели × 2 вида). Для цифровых активов (курсы, модули) часть панелей может быть общими.

## 8. Провайдер сущности (entity-provider)

Чтобы не плодить код, вводится единый контракт:

```ts
interface EntityProvider<E extends EntityKind> {
  kind: E;                                       // 'person' | 'car' | 'real-estate' | 'pet' | 'course' | ...
  resolveInstance(id): Promise<InstanceEntity>;  // мой экземпляр
  resolveType(typeId): Promise<TypeEntity>;      // модель
  linkInstanceToType(instanceId): typeId;        // VIN → модель, ISBN → книга, breed_id → порода
  panels: {
    instance: { top, left, right, bottom };
    type: { top, left, right, bottom };
  };
  modes?: Mode[];                                 // consumer / provider / creator / marketplace
}
```

Новая вертикаль = новый `EntityProvider`. Shell и панели при этом не трогаются.

## 9. Фрактальная грамматика (self-similar)

Shell — лишь верхний уровень **единой самоподобной грамматики**. Ниже (card, panel, section, item, field) применяются те же правила:

- Семь универсальных ролей (Identity / Status / Timeline / Stream / Actions / Evidence / Inversion).
- Два переключателя и только два: **View (⇄)** и **Mode**.
- Шесть канонических жестов (swipe ×2, tap, long-press, pinch, inversion).
- Один закрытый набор layout-компонентов в `packages/ui-react`.

Разница между «машиной» и «кроссовками», между «беременностью» и «модулем кода» — **только в данных**. Полное описание закона — в [17-fractal-ux.md](17-fractal-ux.md). Инварианты I19–I23 в [09-invariants.md](09-invariants.md) обязывают соблюдать эту грамматику на каждом уровне.

## 10. Инвариант

> **Shell не знает про домены. Домены не знают про shell. Между ними — EntityProvider + panel-contract.**
>
> **Вся UI-грамматика (от shell до field) одна и та же для всех сущностей. Новая вертикаль — это новые данные, а не новые правила интерфейса.**

Добавление новой категории (яхты, мотоциклы, музыкальные инструменты, хобби-проекты) — это регистрация ещё одного `EntityProvider` с описанием его `instance.view`, `type.view` и 8 panel-providers. Ни shell, ни чужие домены не переписываются.

## 10. Примеры инверсии

1. Открыл карточку **своей** Camry → Left: бюджет, ТО, страховка. Нажал ⇄ → Left: каталог дилеров/запчастей/тюнинга для Camry 2023.
2. Открыл профиль **актёра** → Right: чат с ним (если он доступен). Нажал ⇄ → Right: сообщества его фан-базы и профессии.
3. Открыл **свою квартиру** → Bottom: журнал счётчиков и заявок УК. Нажал ⇄ → Bottom: новости ЖК и района.
4. Открыл **свой курс, который веду** → Left: мои ученики, выручка, royalty. Нажал ⇄ → Left: витрина курса для покупателей.
5. Открыл **свою собаку** → Left: ветклиника, корм, прививки. Нажал ⇄ → Left: магазин для породы, школы, заводчики.

Всё — один shell, один набор панелей, один принцип.
