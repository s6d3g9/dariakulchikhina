# 17. Фрактальный UX

Главный структурный закон v6: **любой экран, любая карточка, любая панель — построена по одним и тем же правилам**. Пользователь, освоивший интерфейс машины, автоматически умеет пользоваться интерфейсом кроссовок, беременности, модуля кода, яхты, курса. Переход от сущности к сущности не требует обучения заново.

Это не стилистическое требование. Это **архитектурный инвариант**, от которого зависит и UX, и код: один и тот же `Panel<T>`, `CardView<T>`, `SectionStack<T>`, `ActionBar<T>` обслуживают все вертикали. Код компонентов один на всё.

## 1. Уровни самоподобия

Пять уровней, на каждом — одинаковый набор правил.

```
Level 5: Shell                  — 4 панели + центр + switcher + search
Level 4: Card (центр)           — header + timeline + sections + actions
Level 3: Panel (periphery)      — header + stream + filter + action
Level 2: Section (в карточке/панели)
                                — title + stream/grid + more-link + inline-actions
Level 1: Item (атомарный)       — icon + title + meta + action
Level 0: Field (внутри item)    — label + value + unit + hint
```

Каждый верхний уровень — это **композиция** из нижних по единым правилам. Открытие «глубже» никогда не меняет грамматику.

## 2. Универсальная грамматика (семь элементов)

Семь ролей, которые повторяются на каждом уровне:

| Роль | Что делает | Примеры (разные уровни) |
|---|---|---|
| **Identity** | Что это, чьё это, где | title, author, owner, region |
| **Status** | В каком состоянии | active/pending/done, online/offline |
| **Timeline** | История и будущее | roadmap, log, version-history |
| **Stream** | Поток контента | stories, posts, chats, items, reviews |
| **Actions** | Что можно сделать | CTA, inline-buttons, swipe-actions |
| **Evidence** | Артефакты | фото, документы, подписи, чеки |
| **Inversion / Mode** | Сменить угол | ⇄, provider/consumer mode, tabs |

На уровне карточки это секции; на уровне item'а это поля; на уровне поля — визуальные слоты. **Роли одни и те же везде**.

## 3. Инвариант наследования (fractal rule)

> Если X и Y — оба **Entity**, `Panel<X>` и `Panel<Y>` имеют одну и ту же структуру, одни и те же жесты, одни и те же CTA-слоты, одни и те же инверсии.

Следствие: shell-core не имеет kind-специфичного кода. Единственная разница между «машиной» и «кроссовками» — `CardTypeDefinition`, который возвращает разные данные, но через **одинаковые интерфейсы**.

## 4. Правило «две ручки» (Mode × View)

На каждом уровне действуют **ровно две** оси переключения:

1. **View** (⇄): Instance ⇄ Type
2. **Mode**: Consumer / Provider / Creator / Marketplace / Private / Public

Больше осей — запрещено. Если card-type «просит» третий переключатель, это признак, что либо это второй kind, либо это опция внутри Mode.

## 5. Каноничная раскладка центра — CardView

Центральная карточка любой сущности имеет **одинаковую структуру** (6 секций, в одном и том же порядке):

```
┌────────────────────────────────────────┐
│  HEADER   identity + status + ⇄ + mode │  ← один и тот же Identity-блок для всех
├────────────────────────────────────────┤
│  TIMELINE initiation … now … end       │  ← один компонент для машины, курса, беременности
├────────────────────────────────────────┤
│  SUMMARY  key facts, quick metrics     │  ← поля формируются card-type'ом, но компонент один
├────────────────────────────────────────┤
│  ACTIONS primary CTA + secondaries     │  ← один ActionBar с приоритетами
├────────────────────────────────────────┤
│  SECTIONS stack of Streams (evidence,  │  ← один и тот же SectionStack<Section>
│           reviews, related, history)   │
├────────────────────────────────────────┤
│  FOOTER  meta, version, lineage link   │
└────────────────────────────────────────┘
```

Машина, кроссовки, беременность, курс — **одинаковая анатомия**. Card-type только заполняет слоты.

## 6. Каноничная раскладка панели — PanelView

Периферийные панели (top/left/right/bottom) имеют **одну и ту же анатомию**:

```
┌──────────────────────────────┐
│ HEADER  title + filter + ⇄   │  ← всегда top того же вида
├──────────────────────────────┤
│ STREAM  items (Identity+Status│
│         +Meta+Action) loop   │  ← один Item-компонент
├──────────────────────────────┤
│ FOOTER  load-more + quick-CTA│
└──────────────────────────────┘
```

Top-панель в контексте человека (stories) и top-панель в контексте машины (галерея модели) — **одна компонента**, отличается только `content-source`.

## 7. Жесты (ровно шесть)

| Жест | Что делает | Везде |
|---|---|---|
| **Swipe → / ←** | Навигация между панелями или между соседними entity | да |
| **Swipe ↑ / ↓** | Скролл внутри панели или раскрытие/свёртывание панели | да |
| **Tap** | Открыть entity в центр + profile-switch | да |
| **Long-press** | Контекстное меню (share, subscribe, add-to-list, report) | да |
| **Pinch** | Zoom-out из центра в grid соседей / zoom-in в детали | да |
| **Inversion button ⇄** | Сменить View (instance ⇄ type) | да |

Добавлять новые жесты под конкретную вертикаль **запрещено** — иначе фрактальность ломается.

## 8. Цветовая и типографская семантика (единая на всё)

Семантические токены (не цвета!) — одни на всю систему:

```
neutral     — нейтральный контент
primary     — текущий фокус / владелец
accent      — интерактивное действие
success     — завершено / подтверждено
warning     — требует внимания
danger      — проблема / запрет
brand       — type-view (type-bright), делает "модель/бренд" отличимой
private     — только для владельца (замок-иконка, тёмная рамка)
```

Vertical не может ввести собственный цвет. Vertical использует семантические токены. Тему определяет `design-tokens` пакет (светлая/тёмная/контрастная) + опциональный brand-skin в type-view.

## 9. Тексты и копирайт (единая грамматика)

Сообщения построены одинаково:

- CTA: **глагол + объект** («Забронировать слот», «Подписаться на автора», «Оплатить аренду»).
- Denial: **причина + что делать** («Нужен KYC Level 2 — загрузите паспорт»).
- Empty state: **объяснение + действие** («У вас пока нет питомцев — добавить»).
- Ошибка: **что случилось + что делать + trace-id**.

Локализация — per-language, но структура **одна**.

## 10. Интеграция с timeline и creator economy

Фрактальность — не декоративная. Она буквально следует из того, что:

- **Timeline-engine** (`10-timeline-engine.md`) даёт единый формат для всех действий.
- **Creator-economy** (`11-creator-economy.md`) — единый способ мониторизации всего.
- **Pattern-composition** (`12-pattern-composition.md`) — единый способ связывать действия.
- **Policy-engine** (`13-governance-policy.md`) — единый способ ограничивать всё.
- **Shell-entity-model** (`05-shell-entity-model.md`) — единая инверсия для всего.

Все 5 модулей оперируют **одним и тем же Pattern-Card** и **одной и той же Entity**. Фрактальный UX — прямое следствие.

## 11. Проверка самоподобия (ревью-чеклист)

Перед мержем любого card-type или нового UI-компонента — прогон по листу:

- [ ] Пользователь, знакомый только с `person-profile`, может без обучения пользоваться новой card-type.
- [ ] 6 секций CardView присутствуют и в том же порядке.
- [ ] 3 секции PanelView присутствуют для всех 4 панелей и обоих view (instance/type).
- [ ] Не введено новых жестов вне списка §7.
- [ ] Не введено новых цветов вне семантических токенов.
- [ ] Не введено нового переключателя рядом с ⇄ и Mode.
- [ ] CTA-тексты в форме «глагол+объект».
- [ ] Ошибки содержат trace-id.
- [ ] Timeline присутствует, даже если для сущности он «статичный» (created → active → archived).
- [ ] Inversion ⇄ реализована полностью: instance-вид и type-вид оба заполнены.

Непроходной пункт = merge-blocker.

## 12. Антипаттерны

- ❌ Vertical-specific «экран настроек».
- ❌ Уникальный переключатель «вид А / вид Б / вид В» сверху карточки.
- ❌ Кастомный жест «двойной swipe» для конкретного card-type.
- ❌ Свой цвет «для брендинга вертикали».
- ❌ Отличающийся порядок секций в CardView.
- ❌ «Уникальные» табы, которые на самом деле — тот же SectionStack с другим именем.
- ❌ Modal-окна для действий, доступных из ActionBar'а.
- ❌ Скрытый CTA внутри tab'а, до которого 3 клика.
- ❌ Timeline, у которого «нет смысла» — показать хотя бы created → active.
- ❌ Type-view, который «ничем не отличается» от instance-view — значит, card-type плохо смоделирован.

## 13. Код-следствия (компонентный слой)

В `packages/ui-react/` единственные экспортируемые layout-компоненты:

- `<Shell />`, `<ShellCenter />`, `<ShellPanel slot={...} />`, `<ShellSwitcher />`
- `<CardView />`, `<CardHeader />`, `<CardTimeline />`, `<CardSummary />`, `<CardActions />`, `<CardSectionStack />`, `<CardFooter />`
- `<PanelHeader />`, `<PanelStream />`, `<PanelFooter />`
- `<Section />`, `<Item />`, `<Field />`
- `<InversionButton />`, `<ModeToggle />`
- `<SearchBar />`, `<SearchResults />`

Card-type'ы **используют** их и **не определяют** свои layout-компоненты. Если card-type нуждается в чём-то, что не покрывается, — это означает, что **либо вопрос в дизайн-системе** (добавить универсальный компонент), **либо card-type тянет в себя shell-логику** (запрещено).

## 14. Тест на фрактальность

Открытый тест «кроссовки = машина»:

1. Возьми `car` card-type.
2. Возьми `sneakers` (подмножество `clothing-rental` или `collectibles` в type-view).
3. Пройди одинаковые действия на обоих: открыть → inversion → подписаться → форкнуть template «уход» → запустить timeline-план → проверить royalty → перейти в профиль бренда.
4. Если UI-паттерны одинаковые, code-path одинаковый, и tests совпадают на уровне компонентов — **фрактальность сохранена**.
5. Если есть отличие, не являющееся данными — это баг.

Тест автоматизируется: `packages/testing/fractal-harness` проигрывает сценарии для списка card-types и сравнивает UI-snapshot'ы структурно (не пиксельно).

## 15. Инвариант

> **Одна грамматика. Одни роли. Один набор жестов. Одно дерево компонентов. Разные данные.**

Любое отступление — это архитектурная ошибка, не фича.
